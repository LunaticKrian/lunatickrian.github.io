Agent Runtime 核心能力设计

明确 Agent Runtime 执行环境，云端执行 or 本地执行（中心化服务 or 非中心化服务（端服务））

  • 中心化服务需要做好数据隔离，需要花相对比较大的代价去解决数据安全问题。
  • 端服务由于运行在用户本地，只有请求 LLM 时把数据带到云端，天然数据存在部分隔离。端服务带来的是一个升级兼容成本，每一次Agent系统迭代都需要兼容历史版本的用户（强制更新会带来用户体验中断等问题）
  • Agent Loop 核心执行能力（Function Call 工具调用）
  • Agent Context 管理（Context 封装、 Compact）
  • 基于工具调用拓展的能力（Memory记忆，Skill 加载执行机制，MCP 服务，CLI 调用）
  • Sandbox 工具执行环境
  • CFS Workspace 数据安全隔离
  • Muti Agent 架构（复杂任务拆分处理）
  • 基于云端环境，支持 LLM Runs 调用 trace 观测、Steer 消息注入

Context Management​

MCP Registration​

标准化的 MCP 服务注册能力接入

MCP（Model Context Protocol）是围绕 JSON-RPC 2.0 构建的一套开放协议。

MCP的通信模型和基础约定：

  • 三层架构：MCP采用 Host - Client - Server 模型。你的Agent系统是Host（宿主应用），它内部会创建多个Client（连接器），每个Client负责与一个特定的MCP Server建立一对一的连接。
  • 通信基石：所有Client与Server之间的消息必须（MUST） 遵循 JSON-RPC 2.0 规范。这意味着请求、响应和通知都有统一的结构（如jsonrpc: "2.0", id, method, params等）。
  • 传输方式：标准支持两种传输层：stdio（用于本地进程间通信，Server作为Client的子进程）和 HTTP/SSE（用于远程服务）。你的Agent系统需要根据Server的类型选择合适的传输方式。

针对“Agent如何接入外部MCP Server”的场景，将整个流程拆解为注册与发现、获取工具列表、发起调用三个核心阶段。

注册与发现（Discovery）​

发现方式核心机制适用场景与状态
MCP Registry（中心化注册表）官方维护的元数据仓库，提供REST API（如GET /v0.1/servers）供客户端查询可用Server的元数据（名称、位置、能力等）。当前最直接、最主流的方案。适合发现公开可用的Server。它主要被下游聚合器（如市场）消费，你也可以直接调用其API。
Well-Known URI（站点发现）在Server域名下暴露一个标准路径 /.well-known/mcp-server，返回一个JSON清单（Manifest），描述该Server的元数据和安全要求。IETF草案（进行中），旨在让Agent能自动发现某个域名下是否提供MCP服务，实现去中心化的、基于域名的自动发现。
DNS TXT记录（快速发现）通过查询特定域名的TXT记录（如_mcp.domain）来快速获取Server端点或注册表地址，无需先发起HTTPS请求。同样是IETF草案中的补充/快速通道机制，常与Well-Known URI配合使用。

对Agent系统而言：最务实的做法是先集成MCP Registry的REST API来查找和获取目标Server的元数据（server.json），从而得知其传输地址（URL或包名）。

工具列表获取（tools/list）​

通过 tools/list 方法获取Server提供的工具目录：

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/list",
  "params": {
    "cursor": "optional-cursor-value" // 用于分页
  }
}

依据：规范指出tools/list支持分页和缓存。

响应关键字段：

Server会返回一个工具定义数组，每个工具都包含：

  • name：工具的唯一标识符（需遵循命名规范，如长度1-128字符，字符集限制等）。
  • title / description：人类可读的名称和描述。
  • inputSchema：至关重要。这是一个JSON Schema，定义了调用该工具所需的参数结构、类型和约束。你的Agent需要依据此Schema来构造正确的调用参数。
  • icons：可选的图标元数据。
  • 对于2026版本，列表结果还可能包含 ttlMs / cacheScope 等缓存提示信息。

注意事项：

  • 能力声明：Server在注册或元数据中必须（MUST） 声明其支持tools能力，才应该响应tools/list请求。
  • 动态变更：工具列表可能随时间变化。如果Server声明了listChanged: true，它应通过notifications/tools/list_changed通知客户端更新缓存。

发起调用（tools/call）​

Agent 根据用户请求决定使用某个工具后，通过 tools/call 方法发起调用。

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "get_weather", // 来自 tools/list 的 name
    "arguments": {
      "location": "New York" // 必须符合该工具的 inputSchema
    }
  }
}

依据：规范明确调用需指定工具name和符合其inputSchema的arguments。

调用结果处理：

  • 成功响应：result中包含content数组（如text类型的结果）和isError布尔标志。你需要解析content来获取工具执行的实际输出。
  • 处理“输入需求”：在某些场景下，Server可能返回InputRequiredResult，表示完成任务需要额外信息。此时，Client需要收集信息后，携带inputResponses和Server提供的requestState（用于保持状态）重试同一个tools/call请求。注意，重试请求的JSON-RPC id必须不同。

安全考量：规范强调，工具调用应保持“人类在环（Human-in-the-loop）”，即应用应提供UI让用户知晓工具正在被调用，并能拒绝调用。

Agent 安全机制​

安全加固机制：提示词安全（安全段 + 数据/指令隔离 防止提示词注入）；执行边界：沙箱机制 + WorkSpace路径约束；工具治理：让Agent只能看见他能看见的工具；密钥与上下文脱敏；出口审计；HITL；身份隔离。

按 Agent 请求进入、推理、工具调用、执行、结果输出的生命周期划分：

安全层次安全机制主要目标
1. 接入与身份层① 身份认证与访问控制防止未授权用户、设备或服务调用 Agent
② 身份委托与权限传递防止 Agent 越权、混用用户权限
2. 模型与上下文层③ Prompt Injection 防护防止外部内容劫持 Agent
④ 上下文、Session 与 Memory 隔离防止上下文污染、跨用户数据泄漏
⑤ 输入输出安全与 DLP防止敏感数据泄露和不安全结果
3. 工具与能力层⑥ 工具发现、暴露及调用治理控制 Agent 能看到和能执行的能力
⑦ Skill、MCP 与插件供应链安全防止恶意工具和依赖注入
⑧ 多 Agent 委托与协作安全防止子 Agent 权限扩大及横向访问
4. 执行与数据层⑨ 沙箱与 Workspace 约束限制文件、进程和系统资源访问
⑩ 网络出口、浏览器与密钥安全防止 SSRF、数据外传、凭证泄漏
5. 决策与控制层⑪ HITL 与风险分级审批控制敏感或不可逆操作
⑫ 行为约束与资源预算防止无限执行、异常调用和成本失控
6. 运营与治理层⑬ 安全审计、追踪与应急处置发现、追溯和阻断异常行为
⑭ 安全测试与持续加固通过红队测试和安全评估验证防线

这里需要区分三种性质不同的安全能力：

  • 软约束：系统提示词、安全提醒、风险分类器等，降低模型做出危险决策的概率，但不能单独构成可靠的权限边界。
  • 硬约束：身份认证、ACL、工具参数授权、OS 文件权限、沙箱和网络防火墙等，由确定性代码或基础设施强制执行。
  • 监督机制：HITL、日志审计、异常检测、红队测试等，补充对高风险操作和未知攻击的控制能力。

从工程重要性看，通常应优先保证硬约束正确，再利用软约束减少误触发，最后通过监督机制持续发现和处理剩余风险。

Prompt Injection 防护​

对于 Agent 后端工程，值得深入研究的重点不只是 Prompt Injection 防护，而是 Tool Policy Enforcement + Sandbox Isolation + Identity Delegation + HITL 这四种机制如何协同。

Human in the loop​

HIL/HITL（Human in the loop）在Agent的自动化流程中，引入人类的判断、审批或输入，以确保操作的安全、合规与可靠。

在当前的Agent设计范式中，HITL已经从一种简单的“暂停等待”模式，演化为一个包含持久化状态、可编程中断和非阻塞通信的完整工程体系。

范式一：基于中断与检查点（Interrupt & Checkpoint）的持久化暂停​

这是目前主流Agent框架（如LangChain/LangGraph）实现HITL的基础模式。核心思想是让Agent的执行流可以在特定点暂停，将控制权交还给人，并在人类做出决策后从暂停点精确恢复。

  • 实现机制：框架通过中间件（Middleware） 来监控每一次工具调用。当调用命中预设的规则时（例如“写入文件”或“执行SQL”），中间件会发出一个中断（Interrupt），将执行图的状态通过检查点（Checkpoint） 持久化到数据库或内存中。
  • 人类决策类型：在暂停点，人类通常有四种标准化的响应方式，这已成为一种通用语言：
    1. ✅ Approve（批准）：按原计划执行工具。
    2. ✏️ Edit（编辑）：在执行前修改工具的参数。
    3. ❌ Reject（拒绝）：跳过本次工具调用，并向Agent返回拒绝的理由。
    4. 💬 Respond（直接响应）：对于“询问用户”类的工具，直接提供答案，相当于人类代替工具执行。
  • 持久化是关键：由于暂停状态被持久化，即使应用重启、用户刷新页面，Agent也能从断点恢复，而无需重放整个流程。

范式二：工具级审批中间件（Tool-level Approval Middleware）​

这是对上述中断模式的一种策略化封装。它不再需要为每个工具手动编写中断逻辑，而是通过声明式配置来管理。

  • 工作方式：你可以在创建Agent时，通过中间件配置一个策略映射。例如，在LangChain中，可以设置interruptOn规则：对write_file工具允许所有决策（approve/edit/reject/respond），对execute_sql工具只允许approve和reject，而安全的read_data工具则完全不需要审批。
  • 价值：这种模式将安全策略与业务逻辑解耦，让HITL的配置变得集中且可维护，适合需要精细化管理大量工具调用权限的生产环境。

范式三：基于MCP的非阻塞多轮请求（MRTR）​

MCP为HITL提供了协议层面的原生支持，并针对云原生环境进行了关键优化。在2026-07-28版MCP规范之前，常见的做法是保持长连接（如SSE），在内存中“挂起”执行帧等待人类响应，这在负载均衡的分布式环境下非常脆弱。

新的多轮请求（Multi Round-Trip Requests, MRTR） 范式彻底改变了这一点：

  • 核心机制：当Agent需要人类输入时，Server会结束当前的HTTP请求，返回一个“需要输入”的状态和一个不透明的延续值（Continuation Value）。客户端（你的Agent系统）向人类展示问题，在人类回答后，携带这个延续值发起一个新的请求来继续执行。
  • 关键优势：由于请求是无状态和自包含的，任何一个健康的Server副本都可以处理后续的恢复请求，彻底消除了对会话亲和性（Session Affinity）的依赖，使HITL流程在弹性伸缩的云环境中变得健壮。这与你之前了解的MCP无状态生命周期模型是一脉相承的。

Span LLM Agent Trace​

“树形建模、扁平存储”的二元性，是掌握整个系统设计的关键。

在LLM Agent的可观测性体系中，Span模型是对齐执行过程与存储实现的基石。它的核心思路是：将一次Agent运行建模为一棵由Span组成的树（Trace），而存储时则将其“拍平”为扁平的、带有父子指针的记录行。

Span模型 核心组成​

无论基于OpenTelemetry还是其他自研体系，Agent trace的数据模型都建立在两个基本概念之上：

  • Trace（追踪）：代表一次完整的端到端Agent交互，例如从用户输入到最终响应的完整过程。它是一棵有向树，由所有相关的Span构成。
  • Span（跨度）：是Trace中的原子工作单元，代表一个具体的操作，如一次LLM调用、一次工具执行或一次检索。每个Span记录了操作的开始时间、结束时间、名称、属性（Attributes）和状态。

Agent场景的特殊性在于，一个用户请求会递归地扇出（fan-out） 为多次模型调用、工具执行和子Agent交接。因此，Trace必须是一棵树，而非扁平日志，才能保留“什么导致了什么”的因果结构。

生产级存储：分离与分层​

当数据量增大，尤其是LLM调用携带的大文本负载（Prompt/Completion） 时，单纯的扁平行会拖垮存储性能。生产系统通常采用以下模式：

1. 元数据与内容分离（Payload Offloading）

将所有Span共享的轻量元数据（IDs、时间、token数、成本、状态）与笨重的内容负载（prompt messages, completion）分开存储。

  • 元数据：保留在列式数据库（如ClickHouse、DuckDB）的热表中，便于快速扫描、聚合和过滤。
  • 大文本负载：被写入对象存储或独立的内容表，Span行中仅保留一个引用（如内容哈希或外键）。tael-backend的设计明确将prompt和completion作为内容寻址的blob（content-addressed blobs） 处理，以保持列式表的压缩效率和扫描速度。

2. 分层存储（Tiered Storage）

近期数据（如24小时内）放在低延迟的热存储中；更早的数据滚动到不可变的列式文件或冷存储中，以平衡查询性能与存储成本。

3. 增量（Delta）语义

对于成本和Token用量等可累加指标，并非只记录最终值。Span可以在其生命周期内多次发出增量事件（usage delta），聚合操作延迟到查询时进行。这简化了并发写入路径，也保留了流式调用过程中的细粒度消耗信息。

Muti Agent 架构设计​

针对Muti Agent协作的功能场景我认为需要理解的几个核心：

  1. Main-Sub Agents的架构，Main Agent 如何唤起 Sub Agent？（Agent的唤起机制，以及SubAgent Task执行完成之后如何回调Result给MainAgent）（Agent之间的通信机制）
  2. BackGround Task 机制（支持Agent下发任务之后，后台有SubAgents进行任务的执行，MainAgent 挂起等待执行完成，完成之后回复用户。问题点：在云端这种HTTP无状态请求的前提下如何实现这个能力？？？） （后台任务如何下发？主Agent如何挂起和唤醒？）

如何设计一个支持动态 Subagent 创建、并行调度、跨 Agent 上下文隔离、任务恢复、工具权限继承和统一可观测性的 Agent Runtime？？？

从 Agent 后端架构设计的角度，将 Multi-Agent 分为三个层次理解：

  • 协作拓扑（Topology）：Agent 之间如何连接，谁负责调度和决策。
  • 执行编排（Orchestration）：任务如何拆分、并行、交接、检查与终止。
  • 运行时架构（Runtime）：Agent 如何隔离上下文、管理状态、执行工具以及恢复失败任务。

这三个维度是可以组合的，而不是互斥关系。

Muti Agent 设计范式​

Muti Agent Runtime 四种基础架构形态：

基础拓扑核心特点控制权归属SubAgent 机制
Orchestrator–WorkersMain Agent 动态拆分并委派任务Main Agent按需启动 Worker Run
Supervisor / Router专职 Agent 选择、调度专业 AgentSupervisor通常调用预注册 Agent
Network / SwarmAgent 之间对等协作、控制权交接当前活跃 Agent 或协作协议通常使用已有成员，也可动态扩展
Workflow / Graph通过状态图和规则编排 AgentWorkflow Engine通常预定义节点，也支持动态任务分发

对于实际的 Agent 后端研发，更推荐 以中心化 Orchestrator 为主，结合动态 Subagent、DAG 工作流和异步执行的混合架构，而不是直接采用完全自治的 Swarm。这个架构包含几个重要设计原则：

1. Agent 决策与系统调度分离​

Agent 决定做什么，Runtime 控制能否执行以及如何执行。例如：

  • Agent 可以建议启动三个子任务。
  • Runtime 检查并发配额和执行预算。
  • Scheduler 决定并发还是排队。
  • Policy Engine 判断权限是否允许。
  • Executor 负责真正执行。

这样可以避免把权限、安全、重试等重要机制完全交给 LLM 决定。

2. 子 Agent 默认隔离上下文​

不推荐所有 Agent 共享完整 Conversation History。建议让每个 Subagent 拥有自己的短期上下文，仅继承完成任务所必需的信息，最终返回结构化结果和 Artifact 引用。例如：

{
  "task_id": "task_001",
  "agent": "research",
  "status": "completed",
  "summary": "调研结论",
  "artifacts": ["research_report.md"],
  "confidence": 0.87
}

其中 confidence 应明确定义计算来源，不能直接当成可靠的事实概率。

3. 把任务状态做成持久化状态机​

生产系统至少需要区分：

PENDING → RUNNING → COMPLETED / FAILED / CANCELLED

复杂任务还可以加入 WAITING_APPROVAL、SUSPENDED、TIMED_OUT 等状态。

Checkpoint 不仅用于保存聊天记录，还需要恢复执行位置、待处理任务、工具执行结果和审批状态。LangGraph 的 Checkpointer 就是这一类持久化执行设计的具体实现。

4. 区分进程内 Subagent 与远程 Agent​

这是未来架构扩展的重要边界。

维度进程内 Subagent分布式 Remote Agent
调用机制函数、Tool 或 Graph 节点RPC、HTTP、消息队列、A2A
部署通常共享应用 Runtime可独立部署扩缩容
上下文Runtime 管理隔离服务边界天然隔离
延迟通常较低增加网络开销
故障隔离较弱较强，但需处理网络故障
适用单应用复杂任务跨团队、跨系统 Agent

A2A（Agent2Agent）协议解决的是独立 Agent 系统之间的通信、任务委派和结果交换，不直接规定 Supervisor 或 Swarm 等内部编排拓扑。

SubAgent 生命周期​

SubAgent的生命周期其实本质上就包含了：SubAgent初始化创建、SubAgent 任务下发、Main-Sub Agent之间的数据通信、SubAgent Context管理和任务执行、SubAgent资源回收释放。

SubAgent 生命周期是指，在 Main Agent 或 Orchestrator 的委派下，由 Agent Runtime 管理 SubAgent 从实例化、任务下发与调度、任务执行、结果交付、执行终止到资源回收的完整过程。在此过程中，Runtime 持续提供上下文管理、Main–SubAgent 通信、任务状态管理、权限控制和可观测能力，以保障 SubAgent 执行过程的隔离性、可控性、可靠性与可恢复性。
