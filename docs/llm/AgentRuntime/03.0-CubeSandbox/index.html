CubeSandbox API

1.Sandbox Template 模版​

OCI（Open Container Initiative）镜像是一个开放标准的容器镜像格式。

日常使用的 Docker 镜像，绝大多数在本质上就是 OCI 镜像。它的核心目标是确保镜像能在不同的工具和平台间构建、传输和运行，实现互操作性。

一个 OCI 镜像主要由以下部分构成：

  • 镜像清单 (Image Manifest)：一份“目录”，指明了该镜像适用于哪个架构和操作系统，并列出其配置文件和文件系统层。
  • 文件系统层 (Filesystem Layers)：一系列只读的 Tar 包，记录了文件系统的增量变化。这些层叠加起来，就构成了完整的根文件系统。
  • 镜像配置 (Image Configuration)：包含了启动应用所需的信息，如环境变量、默认命令（ENTRYPOINT/CMD）、工作目录等。

这部分内容后续在 Docker 的学习中再深入吧～先有一个基础的认知就行

CubeSandbox 不会像 Docker 那样直接运行 OCI 镜像。它的工作流是：

OCI 镜像 → 模板 (Template) → 沙箱 (Sandbox)

具体转换过程如下：

  1. 拉取与解压：CubeSandbox 从镜像仓库拉取你指定的 OCI 镜像，并解开其所有的文件系统层。
  2. 转换为 rootfs：将这些层合并，转换成一个适合 MicroVM（微虚拟机）启动的 ext4 格式的根文件系统 (rootfs)。这是关键一步，因为 MicroVM 需要的是一个完整的磁盘映像，而非叠加的层。
  3. 启动并制作快照：使用这个 rootfs 启动一个临时的 MicroVM，并运行镜像中定义的启动命令或服务。当通过你设定的就绪探针（Probe）检测到服务完全就绪后，CubeSandbox 会“冻结”此时该 MicroVM 的文件系统、内存和设备状态，生成一个模板快照。
  4. 创建沙箱：之后，每次需要创建沙箱时，都是从这个模板快照快速恢复出一个新的、隔离的 MicroVM 实例。所有对沙箱的写入操作，都会进入一个独立的写时复制（CoW）层，不会影响作为基线的模板。

因此，OCI 镜像是制作模板的输入，而模板才是最终用于创建沙箱的产物。

为什么 CubeSandbox 要采用这种设计？

这种“镜像→模板”的转换，服务于 CubeSandbox 的核心目标：提供接近虚拟机的安全隔离，同时兼顾接近容器的启动速度。

  • 安全隔离的基础：OCI 镜像只包含应用和依赖。CubeSandbox 以此为基础，启动的是一个拥有独立内核的 MicroVM，而非共享宿主内核的传统容器。这带来了本质的隔离等级提升，例如，即便沙箱内的进程尝试危险的系统调用，也只会导致沙箱自身崩溃，而不会威胁宿主。
  • 性能优化的来源：模板快照包含了预热后的内存和进程状态。从快照恢复一个沙箱，远比从零开始启动一个完整的虚拟机要快得多，从而实现毫秒级的启动速度。

MicroVM​

MicroVM（微虚拟机）可以理解为一种 “被极致裁剪过的、专为速度和密度优化的虚拟机”。它保留了传统虚拟机最核心的硬件级隔离优势，同时通过抛弃大量非必要的传统硬件模拟，将启动速度和资源开销压缩到了接近容器的水平。

QEMU 是一个“用软件造电脑”的开源软件。 它能在你现在的电脑里，虚拟出一台完整的“电脑”，然后让 Windows、Linux、Android、嵌入式系统等在这个虚拟电脑里运行。

只为运行一个特定的工作负载而生。它会大幅裁剪虚拟机的“设备模型”，通常只保留最基础的 virtio-net（网络）、virtio-block（存储）和串口控制台等寥寥数个虚拟设备，并配合一个精简的 Guest 内核。这种“极简主义”直接带来了两个结果：

  • 极小的攻击面：设备越少，潜在的安全漏洞就越少。
  • 极快的启动速度：需要初始化的虚拟硬件大幅减少，启动时间可以缩短到百毫秒级。

Guest 内核，就是“运行在虚拟机里的那个操作系统的内核”。 也叫“客户机内核”“来宾内核”。

Guest 内核不是 QEMU 的一部分，而是虚拟机里操作系统自己的内核；它管理的是“虚拟机内部的世界”，不是你的物理电脑。

CubeSandbox 基于 RustVMM + KVM 实现 MicroVM，每个沙箱都运行在一个拥有独立 Linux 内核的 MicroVM 中。

它之所以能达到 60ms 的冷启动和 <5MB 的内存开销，核心在于你上次了解到的“模板”机制：模板本质上是 MicroVM 的一个完整快照（包含内存和进程状态）。创建沙箱时，系统并非从头启动一个 MicroVM，而是直接从快照恢复，从而跳过了所有的初始化步骤。

2.CubeSandbox 核心组件​

官方文档：https://cubesandbox.com/zh/architecture/overview

CubeSandbox 的核心架构可以概括为一句话：一个无状态的控制面，配合一个节点本地的数据面，通过 Redis 完成协调，最终将请求落到 KVM MicroVM 中执行。

理解它的关键，是先建立“控制面 / 数据面”的分层视角，再看每个组件如何在这条链路上各司其职。

(1) 分层设计​

CubeSandbox 的设计原则之一，是控制面无状态、数据面节点本地。

层组件核心职责
控制面CubeAPI、CubeMaster、WebUI、RedisAPI 网关、集群调度、状态协调、运维控制台
数据面Cubelet、CubeShim、CubeHypervisor、CubeVS、CubeCoW、CubeEgress、CubeProxyVM 生命周期、存储、网络、安全策略执行、请求路由

控制面不保存本地状态，Redis 是沙箱元数据与生命周期事件的唯一可信源，因此 CubeAPI 和 CubeMaster 可以轻松横向扩容。数据面则是节点本地的：每个计算节点运行 Cubelet、CubeShim、CubeHypervisor、CubeVS、CubeEgress，管理驻留在该主机上的沙箱。

(2) 核心组件​

PS：要吃透各个组件的具体作用需要较多的时间，这个过程可以放到后续的学习过程中去逐渐完成。当前阶段只需要简单了解有这些组件，这些组件大概的功能是什么即可～

控制面​

CubeAPI（Rust / Axum）—— 统一入口

CubeAPI 是兼容 E2B 的 REST API 网关。它的职责是将 E2B SDK 调用转换为内部 gRPC，处理鉴权回调后转发给 CubeMaster。对使用者来说，只需替换 API URL 等环境变量，就可以从 E2B 云无缝切换到 Cube Sandbox。

CubeMaster（Go）—— 集群级编排调度器

CubeMaster 接收来自 CubeAPI 的沙箱创建、销毁、暂停、恢复请求，依据资源可用性选择目标节点，将工作分发给对应的 Cubelet，并将生命周期事件发布到 Redis。它是整个集群的“调度大脑”，但不直接触碰沙箱本身。

数据面：请求路由与生命周期​

CubeProxy（OpenResty / nginx + Lua）—— 反向代理与请求路由

CubeProxy 是创建完成之后代码执行、文件操作等请求的入口。它从 Redis 读取沙箱元数据，将请求反向代理到正确的沙箱实例。支持两种路由模式：Host 模式解析 <port>-<sandbox_id>.<domain>，路径模式解析 /sandbox/<sandbox_id>/<port>/...。CubeProxy 可多副本扩展，不需要静态配置，副本发现通过 Redis 上的注册表完成。

Cubelet（Go）—— 节点本地生命周期管理器

Cubelet 管理单节点上所有沙箱实例的完整生命周期：创建 → 运行 → 暂停 → 恢复 → 快照 → 销毁。它与 containerd 集成完成镜像拉取，与 CubeCoW 集成完成卷管理。CubeMaster 做出“在哪个节点创建”的决策，Cubelet 负责在这个节点上“把沙箱造出来”。

数据面：虚拟化与执行​

CubeShim（Rust）—— containerd Shim v2 桥接层

CubeShim 实现 containerd Shim v2 接口，是容器运行时抽象与实际 MicroVM 之间的桥梁。它负责沙箱资源准备（rootfs、内存文件、内核）、VM 启动/恢复、vsock 通信，以及用于自动暂停的原地快照。

CubeHypervisor（Rust，基于 RustVMM + KVM）—— 轻量级 VMM

CubeHypervisor 是真正创建和管理 MicroVM 的组件。它管理 vCPU 配置、内存区域、virtio 设备（block、net/vsock、fs），以及启动、暂停、快照与恢复。它经过 seccomp 加固，系统调用面被最小化。CubeSandbox 冷启动 <60ms、额外内存 <5MB 的关键指标，正是由这一层配合预快照模板实现的。

数据面：网络与存储​

CubeVS（eBPF）—— 内核态网络数据面

CubeVS 用 eBPF 程序在内核态完成沙箱的网络转发，替代了传统的 iptables 规则链、Linux Bridge 或 OVS。它提供按沙箱粒度的 SNAT/DNAT、有状态连接追踪、LPM-trie 网络策略，以及点对点 TAP 链路的 ARP 代理。

CubeEgress（OpenResty / Lua）—— L7 出网安全代理

CubeEgress 通过 TPROXY 拦截每一个出站 HTTP/HTTPS 请求，实现域名过滤、凭据注入（密钥永不进入沙箱）和访问审计。沙箱信任由 CubeEgress 签发的根 CA（预置于模板中），从而支持透明 TLS 检查。这是 CubeSandbox“零信任出网”原则的落点。

CubeCoW（Rust）—— 存储引擎

CubeCoW 通过内核 FICLONE ioctl 在 XFS（reflink）上实现 O(1) 快照与克隆，零数据拷贝。模板的 rootfs 和内存卷，都是通过 CubeCoW 以 reflink 方式被沙箱“克隆”出来的；快照仅持久化脏页，未变更页继续共享。

(3) Sandbox.create() 执行流转​

关键分岔点在于：

  • 创建/销毁/暂停/恢复走的是 CubeAPI → CubeMaster → Cubelet → CubeShim → CubeHypervisor 这条控制面到数据面的管理路径；
  • 创建完成后的代码执行、文件读写，则通过 CubeProxy 直接路由到沙箱，不经过 CubeMaster，避免了所有运行时流量都挤过中央调度器。

3.CubeSandbox 生命周期​

了解了 CubeSandbox 中的 Template 机制之后，后续需要了解 CubeSandbox 是如何调度模版拉起虚拟环境进行代码执行的？

一个代码执行请求在 CubeSandbox 中的旅程，可以清晰地分为接入与调度、沙箱准备、代码执行、生命周期管理四个阶段。核心调度思想是“分布式调度 + 单机装箱”，控制面与数据面各司其职。

with Sandbox.create(config=config) as sandbox:
    result = sandbox.run_code("1 + 1")
    print(result.text)

阶段一：接入与调度​

调用 Sandbox.create(config=config) 时，请求首先会进入控制面（Control Plane）。

控制面的核心组件是 CubeAPI（对外提供 REST API，如端口 3000）和 CubeMaster（负责节点注册、模板管理、调度与元数据）。这个阶段的核心任务是决定“在哪台物理机上创建沙箱”：

  • 中心分布式调度：CubeMaster 接收创建请求后，会基于一致性哈希等策略进行请求分片，将请求路由到某个调度节点。如果某节点负载过高，动态权重机制会将其转发至轻载节点。
  • 节点本地装箱：请求到达目标物理节点后，节点上的本地服务（如 Cubelet）会检查本地资源池。Cube 的设计让单节点具备超过 1K 的沙箱密度，资源池（物理资源池、虚拟资源池、组件资源池）提前预备好，沙箱生产就像“从池中取件组装”。如果本地资源充足，就直接在本地完成装箱，避免将请求打回中心调度层，从而将调度延迟稳定在极低水平（如 3ms 以内）。

这种“中心派单 + 本地消化”的双层结构，是 Cube 能够线性扩展并发能力的关键。

阶段二：沙箱准备（从快照到可服务的 MicroVM）​

从快照到可服务的 MicroVM。这里为啥是快照，而不是 Template？

CubeSandbox 官方对“模板”的定义是：“它不仅包含来自 OCI 镜像的根文件系统，还包含沙箱启动所需的配置和预热后的 MicroVM 快照”。

调度决策完成后，沙箱的“生产”在目标节点上极速完成。Cube 的沙箱是 KVM MicroVM，其准备过程之所以能控制在百毫秒级，依赖几个核心设计：

  • 快照恢复 + Lazy Load：所有沙箱都基于模板快照恢复创建。沙箱内部系统完全无状态（状态保存在虚拟化后端），因此沙箱自身的恢复与后端配置刷新可以并发进行，端到端交付一个可服务沙箱只需百毫秒左右。基于 EPT 页表的lazy load 机制，快照未触及的内存页会延迟到真正需要时才建立映射，进一步加速启动。
  • 进程拉起：创建请求到达 Cubelet 后，VM 内的 cube-agent（PID 1） 会拉起 envd。envd 就是后续代码执行的数据面入口，驻留在沙箱内部。

至此，一个拥有独立内核、文件系统和网络的全隔离 MicroVM 已经就绪，Sandbox.create() 返回，with 语句块开始运行。

阶段三：代码执行​

with 块内的 sandbox.run_code("1 + 1") 走的是与创建完全不同的数据面（Data Plane） 通道，其路径更短、更直接：

  • 请求路由：run_code 请求由 E2B SDK 发出，经由 CubeProxy（数据面入口），通过 WSS/HTTP 直接路由到目标沙箱内部的 envd。控制面（CubeMaster）不参与这次代码执行的调度，实现了控制与数据分离。
  • 沙箱内执行：envd 收到请求后，调用沙箱内的 Code Interpreter 执行 "1 + 1"。由于沙箱本身是一个完整的 MicroVM，代码运行在完全隔离的内核环境中，不会影响宿主机或其他沙箱。
  • 结果返回：计算结果 2 沿原路返回，作为 result.text 输出。

这条数据面路径的设计，使得代码执行的延迟极低，且不会与控制面的管理操作（如创建、销毁）相互干扰。

阶段四：资源回收（with 块退出之后）​

当 with 块结束时，Sandbox.create 创建的沙箱会触发自动销毁流程。但这只是 Cube 生命周期管理的一种模式。在更贴近真实 Agent 场景的部署中，Cube 提供了更精细的三段式生命周期：

  • 创建：首次执行代码时创建沙箱，并写入会话/租户元数据。
  • 保活（Pause/Resume） ：沙箱默认在15 分钟无调用后，由 on_timeout=pause 策略自动暂停（对 VM 做内存快照）。下一条消息到来时，auto_resume=true 会自动恢复，且工作目录原样可用。这避免了频繁冷启动，同时释放了活跃占用的资源。
  • 回收（Reclaim） ：平台侧的生命周期循环每 60 秒扫描一次，只回收同时满足“带平台会话标记”且“已 paused”的沙箱，避免误删仍在会话中的实例。

这种“短暂保活 + 自动暂停 + 安全回收”的模式，在“用完即毁”的 Serverless 模型和“有状态会话”的 Agent 需求之间取得了平衡。

CubeSandbox 资源分析​

对比一下 OpenSandbox（alibaba开源的Sandbox基础环境）之间的性能差距，总结一下生产环境迁移之后的性能对比分析。重点：比较 OpenSandbox 与 Cube Sandbox，说明迁移动因、业务匹配、性能、安全、风险以及未选择方案的理由。

生产环境：10台物理节点（单台物理节点资源：48核 + 256G）

OpenSandbox 启动机制​

OpenSandbox的标准Kubernetes运行时，其创建沙箱的典型流程确实带有“冷启动”的特征。官方文档指出，这条路径的延迟通常在2到5秒，主要耗时在以下几个环节：

  • 镜像拉取（1-10秒） ：如果目标节点上没有缓存所需镜像，就需要从仓库拉取，这是最大的不确定性来源。
  • K8s调度延迟（~100-500ms） ：Kubernetes Scheduler需要为Pod选择节点。
  • etcd写入与事件传播（~50-200ms） ：通过K8s API创建资源带来的开销。
  • Kubelet创建Pod与容器运行时启动（~1-3秒） ：这是容器化本身固有的初始化时间。

所以，如果单纯看标准路径，遵循了“拉镜像 → 启动容器”的传统模式。

OpenSandbox 也提供了不少优化机制来提供沙箱的创建效率：
  • 预热池（Warm Pool）：针对标准K8s路径，OpenSandbox提供了预热池（Pool） 机制。其原理是预先创建好一批运行着指定镜像的Pod，当创建请求到来时，直接从池中分配一个已经启动的容器，从而消除镜像拉取、Pod调度和容器初始化的时间
  • fast-sandbox运行时：fast-sandbox运行时完全绕开了Kubernetes控制面在创建沙箱时的“热路径”（Scheduler → etcd → Kubelet），通过gRPC Fast-Path API直接与节点上的Agent通信，由Agent直接调用containerd的socket来创建容器。在镜像已缓存的前提下，这条路径可以将容器创建延迟压缩到50毫秒以内。它的核心思路是优化控制链路，而非改变容器本身的启动语义。镜像未缓存时，仍然需要承担拉取时间。
  • Firecracker MicroVM 的快照恢复：遵循“创建即恢复”的理念，从预先准备好的、已达就绪状态的VM快照直接恢复，而非启动一个新的实例。E2B、CubeSandbox以及OpenSandbox的FC路径都采用了这一模式。此外，OpenSandbox还实验性地支持QEMU VMState快照，可以保存和恢复QEMU虚拟机的内存、vCPU等完整状态，实现进程级的暂停与恢复。

CubeSandbox 迁移分析​

OpenSandbox 标准 K8s 路径 2–5 秒，CubeSandbox 的冷启动速度比 OpenSandbox 快 2.5 到 50 倍。

线上的沙箱集群不稳定，老是出现 K8S 调度失败出现 Sandbox Pod init和 Terminating 卡住。定位的具体原因是：

Q1：为什么想从 OpenSandbox 迁到 CubeSandbox？

答：核心是业务形态匹配。我们的沙箱是高频创建、短任务、用完即毁。OpenSandbox 走 Kata 路径时，每次创建都要付完整 VM 启动成本，短任务下这个固定开销被反复放大。CubeSandbox 用模板快照恢复 MicroVM，冷启动几十毫秒，密度也更高。所以迁移动因是“结构性开销”不匹配，不是 OpenSandbox 本身不能用。

OpenSandbox 走 Kata 路径，怎么理解这个 Kata路径？

Q2：OpenSandbox 不是有 fast-sandbox 吗？为什么不用？

答：有，fast-sandbox 可以做到低于 50 毫秒，性能上不是没有解法。但它需要专用运行时和额外部署维护。我们评估的是“迁移收益 vs 运维复杂度”。如果团队不想放弃 K8s 生态，OpenSandbox + fast-sandbox 是必须保留的对照方案；如果业务更看重默认开箱即速和单机密度，CubeSandbox 更合适。

Q3：性能收益到底有多大？怎么验证？

答：公开数据上，CubeSandbox 官方冷启动约 47.8 毫秒，P95 约 57.4 毫秒；第三方测试 72–78 毫秒。OpenSandbox 标准 K8s 路径 2–5 秒，池化约 1 秒，fast-sandbox 可低于 50 毫秒。所以对比不能笼统说“快多少倍”，要看 OpenSandbox 选哪个运行时。验证上我会用真实业务镜像和任务脚本，按并发 1、20、50 三档压测，重点看 P95/P99、任务完成耗时和单实例实际内存增量，不只看平均值。

Q4：高并发下 CubeSandbox 有没有问题？

答：有需要正视的点。官方基准里 50 并发下单条创建 P95 会到约 508 毫秒，P99 约 681 毫秒，虽然总吞吐还不错，但单次尾延迟明显变长。所以如果业务对单次创建 SLO 很严，必须压测高并发档位，不能拿低并发的 48 毫秒直接外推。

Q5：安全上迁移是提升还是风险？

答：要分情况。如果原来 OpenSandbox 用的是 runc，CubeSandbox 默认 KVM 硬件隔离是实质提升；如果原来已经用 Kata Firecracker，两者隔离量级相近，安全增量有限。CubeSandbox 有一个已披露漏洞：v0.5.1 之前 host-mount 元数据可被滥用挂载宿主机路径，所以目标版本必须 ≥ v0.5.1，并且升级后要独立验证路径约束生效，不能只看版本号。

Q6：迁移最大的风险是什么？

答：最大的风险不是性能，而是两个“假设”。第一，CubeSandbox 兼容的是 E2B 协议，不是 OpenSandbox 协议，现有代码不一定改个 URL 就能跑，可能需要适配层。第二，沙箱从 K8s 资源变成 Cube 自己管理的 MicroVM，监控、告警、资源配额、故障恢复都要重新接。性能风险反而可以通过压测提前量化。

Q7：10 台物理节点算大规模吗？

答：不算。10 台 48 核 256G，总共 480 核 2.5T 内存，对比业界大规模沙箱集群是中小规模或生产起步规模。OpenSandbox 官方说能扩到数百节点，10 台在它的中段；对比 DeepSeek 公开的约 160 节点、3 万核、250T 内存的生产单元，我们差一到两个数量级。所以面试里我会说“中等规模生产集群”，不说大规模。

Q8：为什么没有继续优化 OpenSandbox？

答：我们评估过继续优化 Kata 路径、自建 MicroVM、其他方案和 CubeSandbox。继续优化 OpenSandbox 的问题是 Kata 路径的固定开销是结构性的，池化能降低部分等待，但 Pod 调度和 VM 启动的粒度还在。短任务足够高频时，优化边际收益递减。不过我们没有把 OpenSandbox 一票否决，而是保留它作为对照方案，因为它的 K8s 生态和多语言 SDK 更完整。

Q9：如果迁移失败，怎么回退？

答：分两层。业务层通过适配层隔离沙箱协议，避免业务代码直接绑死 CubeSandbox；基础设施层保留 OpenSandbox 集群和镜像模板，PoC 阶段双跑，按真实任务做 A/B。回退触发条件提前定好，比如 E2B 接口覆盖有关键缺口、50 并发 P95 超 SLO、或运维告警接线成本超预算。

Q10：你怎么判断业务是否匹配 CubeSandbox？

答：看三个特征：创建频率高不高、单任务生命周期短不短、对冷启动和密度敏不敏感。高频短任务、延迟敏感、需要强隔离，匹配度高；长任务、重 K8s 统一管控、强依赖 Java/Go 等多语言原生 SDK、或者有 ARM 节点，就要谨慎。CubeSandbox 的 PVM 内核是 x86_64 only，ARM 场景要单独评估。
