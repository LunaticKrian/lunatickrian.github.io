01.4 Anthropic Agent Evaluation

原文地址《Demystifying evals for AI agents》：https://www.anthropic.com/research/demystifying-evals-for-ai-agents

感兴趣可以阅读一下原文，我个人认为 Anthropic 这篇文章主要是在理论层面上对 Agents Evaluation 的概念进行了详细的解析。与实际在企业中实践落地还是有一定距离感，文章并没有揭露 Anthropic 内部构建 Agents Evaluation 的完整体系结构（毕竟 Evaluation 也是大大提升 Agent/LLM 效果的一个重要环节，肯定不会轻易泄露）。

本文详细的转述了《Demystifying evals for AI agents》原文的核心内容，并在此基础上新增个人的认知与理解和在企业实践环节中的经验。至于其中正确性需要读者自行判断，如有问题欢迎一起探讨交流～

Why？为什么构建 Evaluation？​

真实且体会深刻，痛苦不堪......死去的回忆又开始攻击我了！！！

当团队刚开始开发智能体时，通过手动测试、内部测试以及直觉判断，他们往往能够取得相当不错的进展。更为严格的评估方式似乎只会增加工作量，从而延缓产品的推出速度。但在初期原型开发阶段过后，一旦智能体开始投入实际使用并逐步扩展规模，如果不进行评估，其功能就会出现问题。

通常，临界点出现在用户反馈说系统在经过修改后表现更差时。此时团队处于“盲目操作”的状态，除了猜测和测试之外，没有其他方法来验证问题所在。由于缺乏评估机制，调试工作只能被动进行：等待用户投诉、手动复现问题、修复错误，同时希望不会出现其他问题。这样的团队无法区分真正的功能退化与偶然现象，也无法在发布前对各项更改进行数百种场景的自动测试，更无法衡量改进效果。

我们已经多次目睹这种发展过程。例如，Claude Code 最初是依据 Anthropic 员工及外部用户的反馈来快速进行迭代的。后来，我们加入了各种评估机制——起初是针对简洁性、文件编辑等简单功能进行评估，之后则针对过度设计之类的更复杂问题进行评估。这些评估有助于发现存在的问题、指导改进方向，并促进研发团队与产品团队之间的协作。结合生产环境监控、A/B 测试、用户研究等多种方法，这些评估机制能够为持续优化 Claude Code 提供有力支持。

在智能体的整个生命周期中，进行性能评估都十分有用。在早期阶段，评估能促使产品团队明确什么是智能体的成功标准；而在后期，则有助于保持一致的质量水平。

在智能体开发初期，评估机制尤为重要，因为它有助于明确界定智能体应有的行为方式。即便两名工程师阅读相同的初始需求文档，也可能会对人工智能应如何处理各种边缘情况有不同的理解。而评估机制就能消除这种歧义。无论何时创建，评估机制都能帮助加快开发进度。

评估机制还会影响采用新模型的速度。当更强大的模型出现时，没有评估机制的团队需要花费数周时间进行测试，而那些拥有评估机制的竞争对手则能迅速了解该模型的优势，调整相关参数，并在几天之内就能升级到新模型。

一旦有了评估机制，就能免费获得各种基准数据和回归测试结果：可以追踪延迟、令牌使用量、每项任务的成本以及错误率等指标。这些评估机制还能成为产品团队与研究团队之间的高效沟通渠道，为研究人员提供优化目标。显然，评估机制带来的好处远不止于追踪系统的退化或改进情况。由于成本在初期就能显现，而好处则需一段时间后才能体现出来，因此其综合价值很容易被忽视。

Evaluation 结构​

Evaluation 评估是指针对人工智能系统的测试过程：给人工智能系统输入某种指令，然后根据系统的输出结果来判断其性能是否达标。在本文中，我们重点讨论在开发过程中无需真实用户参与即可进行的自动化评估。

  • 一次性评估（Single-turn evaluations）非常直观：一个提示、一个响应，然后就是评分逻辑。对于早期的大型语言模型来说，一次性、非代理式的评估是主要的评估方式。随着人工智能能力的不断提升，多轮次评估变得越来越常见了（其中主要是针对上下文关联信息的理解处理，通常代词等语义理解）。
  • 智能体的评估（Agent evaluations）更为复杂。它们会在多轮互动中使用各种工具，改变环境中的状态，并不断调整自己的策略——这就意味着错误有可能不断累积、愈发严重。而前沿模型则能够找到创造性的解决方案，从而超越传统评估方法的局限。

在简单 Single- turn 的 Evaluation 中，LLM 会处理 Prompt，而评分器则负责判断输出结果是否符合预期。

在更复杂的 Agent 多轮评估中，Agent 会接收工具、任务（在本例中为构建 MCP 服务器）以及环境信息。Agent 会执行一系列工具调用和推理过程，并根据实现结果更新环境。最后，评分器会通过单元测试来验证构建出的 MCP 服务器是否正常工作。

Agent Evaluation Anthropic 提出了如下的定义：

  • Task（Prompt、Test Case）：具有明确输入和成功标准的单次测试。
  • Trial：每次尝试完成某项任务都算是一次试验（Trial）。由于模型在不同运行次数下的输出结果会有所不同，因此我们需要进行多次试验，以获得更稳定的结果。
  • Grader：评分器（grader）是一种用于评估智能体性能某方面的逻辑机制。一个任务可以配备多个评分器，每个评分器又包含多个判定条件（有时也称为检查项（check））。
  • Transcript（trace、trajectory）：trace 是对一次 Trial 过程的完整记录，其中包括输出结果、工具调用信息、推理过程、中间结果以及各种其他交互内容。其中包含了所有对 API 的调用以及 Trial 过程中返回的所有响应。
  • Outcomes：是 Trail 结束时环境中的最终状态。虽然航班预订 Agent 可能会在对话结束时说“您的航班已成功预订”，但真正的结果则是该预订记录是否真的存储在数据库中。
  • Evaluation harness：是用于实现端到端评估的基础设施。它提供相应的指令与工具，能够同时执行多项任务，记录所有操作步骤，对输出结果进行评分，并汇总最终结果。
  • Agent Harness（scaffold）是一种能够让模型以 Agent 形式运行的系统：它负责处理输入数据、协调各种工具的调用，并返回处理结果。当我们评估某个“Agent”时，实际上是在评估该框架与模型共同作用的效果。
  • evaluation suite：一组用于衡量特定能力或行为的任务，这类任务通常具有共同的目标。

How？怎么进行 Agent Evaluate？​

对于每项任务，评分方式可以是加权式（所有评分者的得分需达到特定阈值）、二元式（所有评分者都必须通过），或是混合式。

目前，有几种常见的智能体被大规模应用，包括编程智能体、研究智能体、计算机操作智能体以及对话智能体。这些智能体可以应用于各种行业，但可以用类似的方法来对它们进行评估。无需从头开始设计评估方法。下文介绍了针对这几类智能体的成熟评估技术，可将这些方法作为基础，再根据具体需求进行扩展。

三种评测机制​

Code-based graders 基于代码的评分工具​

基于代码的评分器，本质上是用写死的确定性程序逻辑、规则或测试脚本，直接检验 Agent 的输出结果以及它对外部环境造成的最终状态变化。在工程实践中，它常见于精确匹配或正则校验、单元测试与集成测试（例如运行 pytest 验证代码是否正确）、静态代码分析（如 ruff、mypy、bandit）、系统与数据库状态校验（如核实工单状态已变更为已解决、文件已正确生成、安全日志已写入），以及针对运行轨迹的硬性约束（如限制最大对话轮数、检查关键工具参数是否合规）。

这类评分器的最大优势在于速度极快、运行成本几乎为零，而且结果百分之百客观、完全可复现，非常适合无缝集成到 CI/CD 流程中，在每次代码提交时自动高频触发。但它的短板同样明显：规则相对死板且容易脆弱，只擅长验证有明确标准或固定形态的任务。面对表达方式多样、存在多种合理路径的开放性问题时，它很容易误杀有效解法，也完全无力评估沟通语气、推理连贯性或代码可读性等软性指标。因此，它最适合承担编程任务正确性校验、业务数据落库检查以及客观事实精准抽取等确定性场景。

Model-based graders  基于模型的评分器​

基于模型的评分器，是指引入另一个大模型充当裁判，结合预先定义好的评分细则（Rubric）或自然语言断言，对被测 Agent 的最终产出或完整交互轨迹进行打分与判定。常见用法包括按准确性、完整性、语气等维度进行结构化打分，用自然语言断言核查特定行为（例如判断客服是否对客户情绪表达了共情、回答是否严格基于检索工具结果），对新旧两个版本的输出做盲评对比，或者在不苛求字面完全一致的前提下判断答案与参考解是否语义等价。

它的核心优势在于高度灵活，能够真正理解复杂语义、上下文语境以及开放式表达，弥补了纯代码无法评判主观质量与交互体验的盲区，同时依然保持了自动化、可规模化批量运行的效率。不过，相比纯代码方案，模型评分器更慢、成本更高，且容易受到模型随机性、幻觉或固有偏好（如偏爱冗长回答）的影响。为了用好它，实践中通常需要将评分拆解为清晰的结构化子维度、尽量用彼此独立的模型分别评判不同维度、允许模型在信息不足时输出“Unknown”以减少胡猜，并持续与人类专家的评判进行校准。这类方法非常适合评估对话代理的沟通体验、研究报告的覆盖度与逻辑连贯性，以及存在多种“正确答案”的开放任务。

Human graders  人工评分员​

人工评分员是指由人类——包括研发和产品团队成员、经过专门培训的标注人员，或医疗、法律、金融等领域的专业人士——直接阅读 Agent 的最终输出或完整运行记录（Transcripts），从而给出定性诊断或结构化评分。在落地形态上，它既包括团队日常抽查失败案例、建立直觉的“人工审查运行记录”，也包括多名评分者按统一标准交叉盲评、对齐分歧的“系统性人工评估研究”。

人工评分公认是整个评估体系的“黄金标准（Gold standard）”，因为它最贴近真实人类体验与复杂业务意图，既能驾驭高度模糊、主观或专业门槛极高的前沿任务，也是及时发现评分器漏洞与评估体系缺陷的不可替代手段。然而，人工评估的成本最高、反馈周期最慢、难以高频大规模开展，而且容易受到评审者疲劳度与个体标准差异的影响，多人意见分歧也需要额外的仲裁协调机制；遇到高门槛垂直行业时，更是必须聘请稀缺的领域专家。因此，人工评分员主要活跃在项目早期定义质量标准、高风险专业领域把关、深挖疑难失败根因，以及为大模型评分器提供校准基准的场景中。

在真实 Agent开发中，这三类方法并非互相替代，而是呈金字塔式分层协作：

  • 凡是能客观验证的结果和状态，坚决优先交给基于代码的评分器去高频跑全量、守住底线；
  • 代码评不了的语义、体验与综合质量维度，则交给经过校准的大模型评分器实现规模化自动评判；
  • 而人工评分员不应被消耗在全量重复测试上，而应当站在体系顶端扮演“裁判长”——负责定义最初的质量标尺、定期抽读运行记录查漏补缺，并持续校准模型评分器的准确度，一旦自动化体系足够稳健，人工只需保持低频抽检即可。

Agents 类型分类​

编程代理（Coding Agents）​

核心特点与评估逻辑：编程代理像人类开发者一样浏览代码库、编写代码、运行命令并调试错误。这类任务的评估相对直接，因为软件工程天然具备清晰的客观验证标准：代码能否顺利运行、测试是否全部通过。因此，高质量的编程代理评估通常建立在定义明确的任务、稳定的测试环境以及完备的代码测试用例之上。

主流方法与代表基准：确定性评分器（Deterministic graders）是编程代理最自然的选择。目前最具代表性的两大基准均遵循这一思路：SWE-bench Verified 为代理提供流行 Python 开源仓库中的真实 GitHub Issue，通过运行项目测试套件来评分，只有同时修复失败用例且不破坏原有测试才算通过（仅用一年时间，大模型在该基准上的表现就从 40% 跃升至 80% 以上）；Terminal-Bench 则侧重另一维度，专门考察端到端的复杂技术工程任务，例如从源码编译 Linux 内核或训练一个机器学习模型。

实战要点与示例：在基础的“通过/失败”测试之外，对运行轨迹（transcript）进行附加评估同样很有价值，例如借助静态分析规则考察代码质量，或用大模型评分器依据清晰标准评估工具调用和交互表现。文中以“修复空密码或空值导致的鉴权绕过漏洞”为例，展示了可组合的完整评估配置，涵盖单元测试、大模型代码质量评分、静态分析工具（ruff、mypy、bandit）、安全日志状态检查以及关键工具调用校验，同时追踪对话轮数、工具调用次数、总 Token 消耗以及首尾 Token 延迟和输出速率等指标。但在真实业务落地中通常不必面面俱到，一般以单元测试校验正确性加上大模型评分标准评估整体代码质量为主，其余评分器和指标按需引入即可。

对话代理（Conversational agents）​

核心特点与评估逻辑：对话代理主要活跃在客服、销售、辅导等场景中。与传统问答机器人不同，现代对话代理需要在多轮交互中持续维护状态、调用外部工具并实时执行业务操作。它面临的独特挑战在于，交互过程本身的质量就是评估对象的一部分，而不仅仅看最终结果。此外，对话评估通常还需要引入第二个大模型来扮演模拟用户，例如 Anthropic 在构建对齐审计代理时，就通过让模拟用户与被测模型展开长周期、对抗性对话来进行压力测试。

主流方法与代表基准：对话代理的成功标准本质上是多维的，需要把可验证的最终状态与交互体验结合起来——例如工单是否真正解决（状态检查）、是否在规定轮数内完成（轨迹约束）以及回复语气是否得体（大模型评分）。代表基准 τ-Bench 及其升级版 τ²-Bench 正是围绕这种多维性设计的，它们在零售客服、机票预订等仿真业务中，由一个模型扮演特定用户画像，考验代理在真实多轮对话中的综合应对能力。

实战要点与示例：文中以“安抚情绪焦躁的客户并办理退款”为例，综合配置了多类评分维度：用大模型评分检查代理是否表达共情、方案解释是否清晰、回复是否严格基于政策查询工具的返回结果；用系统状态检查确认工单已解决且退款已入账；用工具调用检查验证身份核验、限额退款和确认通知等动作是否合规；并限定总对话轮数不超过 10 轮，同时监控轮次、Token 与延迟指标。在实践中，由于许多对话类任务（如咨询解答）往往存在多种同样合理的“正确答案”，因此通常核心依赖基于模型的评分器来同步衡量沟通质量与目标达成度。

研究代理（Research agents）​

核心特点与评估逻辑：研究代理负责信息搜集、综合提炼与深度分析，并最终输出结论或研究报告。与编程代理能靠单元测试给出非黑即白的判定不同，研究质量高度依赖具体任务语境——市场扫描、并购尽职调查和科研综述对“全面”“有据可查”乃至“准确”的界定截然不同。这带来了三重独特挑战：即便是人类专家，对一份综合报告是否足够全面也常常看法不一；外部参考信息随时更新，导致所谓“标准答案”不断漂移；而更长、更开放的文本输出本身也大幅增加了出错空间。

主流方法与代表基准：在开放网络检索领域，BrowseComp 等基准专门测试代理在海量网页中“大海捞针”的能力，其题目刻意设计为“极难解答但易于验证”。针对更广泛的研究任务，主流做法是组合多种评分机制：通过事实依据检查（Groundedness checks）核实论断是否真正有检索来源支撑；通过覆盖度检查（Coverage checks）确保回答涵盖了必备的关键事实；通过来源质量检查（Source quality checks）确认引用的是权威信源，而非随手抓到的第一条搜索结果；而对于有唯一客观答案的事实型问题（如某公司第三季度营收），则可直接采用精确匹配（exact match）。

实战要点与示例：大模型评分器在研究代理评估中扮演核心角色，既能标记缺乏依据的断言与内容缺口，也能从整体上评估开放式报告的连贯性与完整性。但正因为研究质量带有显著的主观色彩，团队绝不能将大模型评分规则一劳永逸地放任不管，而必须频繁与人类领域专家的评判进行校准，才能保证评估结果的可靠度。

计算机操控代理（Computer use agents）​

核心特点与评估逻辑：计算机操控代理不依赖底层 API 或代码接口，而是像人类用户一样直接通过屏幕截图、鼠标点击、键盘输入和页面滚动来操作软件，因而能够驾驭从专业设计工具到老旧企业软件的各类图形界面（GUI）应用。评估这类代理必须在真实或沙盒环境中让它实际操作目标软件，并通过检查环境变化来判断是否真正达成了预期任务结果。

主流方法与代表基准：WebArena 和 OSWorld 是该领域的两大代表基准。WebArena 聚焦浏览器任务，除了通过 URL和页面状态验证代理是否正确导航外，还会针对修改数据的任务做后端状态校验——例如核实订单是否真的写入了后台，而不是仅仅停留在看到了“下单成功”页面的表面现象。OSWorld 则进一步将考察范围扩展到完整的操作系统控制，在任务完成后通过专门的评估脚本，全面检查文件系统状态、应用程序配置、数据库内容以及界面元素属性等各类底层产物。

实战要点与示例：在浏览器操控等实际落地场景中，评估不仅要看结果对不对，还要关注Token 效率与响应延迟之间的精细权衡。基于页面 DOM 树的交互方式执行速度很快，但容易消耗大量Token；基于视觉截图的交互速度较慢，但在复杂页面下反而更省 Token。例如让 Claude 总结维基百科词条时，直接读取 DOM 提取纯文本最高效；而在亚马逊上挑选一款新笔记本电脑包时，抓取整个庞杂页面的DOM 会耗费极高 Token，改用截图方式反而更划算。Anthropic 在开发 Claude for Chrome 产品时，就专门设计了针对工具选择能力的评估，检验代理能否根据当前页面场景选对最合适的交互方式，从而显著提升了浏览器任务的执行速度与准确率。

总体而言，四类 Agent的评估设计呈现出从高度确定性验证向多维与主观综合评判延伸的光谱：编程与计算机操控代理高度依赖可验证的系统最终状态与自动化测试，对话代理额外需要引入用户模拟并把交互体验纳入评分，而研究代理则最强调多维证据核验与高频的人类专家校准。

Evaluation 指标​

Agent 的自主性、多轮工具调用和环境交互能力，使传统 LLM 评估方法失效；需要一套以“结果”为中心、分层使用评分器、并用真实失败案例驱动的评估工程体系。

Agent 的执行过程是带有不确定性的，因此不能想传统服务或者NLP模型一样进行评估测试，其行为在每次运行时都会发生变化，这使得评估结果比看上去更难以解读。每项任务都有各自的成功率——某个任务的成功率可能是 90%，而另一个任务则为 50%；在某次评估中能够完成某项任务的代理，在下一次评估中却可能失败。有时，我们想要了解的是代理完成某项任务的频率（即成功尝试的比例）。

有两个指标有助于体现这一细微差别：
  • pass@k 衡量的是代理在 k 次尝试中至少得到一次正确解的概率。
  • pass^k 表示所有 k 次尝试都成功的概率。

pass@k​

pass@k 用来衡量智能体在 k 次尝试中至少能找到一个正确解的概率。随着 k 值的增加，pass@k 的得分也会上升：尝试次数越多，至少能成功一次的概率就越高。

如果 pass@1 的值为 50%，那就意味着该模型在第一次尝试时就能完成一半的测试任务。在编程领域，我们通常更关注智能体能否在第一次尝试时就找到解决方案——也就是 pass@1 的情况。而在其他情况下，只要有一个解决方案是有效的，那么提出多个解决方案也是可以的。

pass^k​

pass^k 表示所有 k 次尝试都能成功的概率。随着 k 值的增加，pass^k 的值会下降，因为要在更多次尝试中保持成功率，难度也会随之上升。

如果某个智能体的单次尝试成功率为 75%，而进行 3 次尝试的话，那么全部成功的概率为(0.75)³，约为 42%。对于那些需要为用户提供稳定服务的智能体来说，这一指标尤为重要，因为用户期望它们每次都能可靠地工作。

随着试验次数的增加，pass@k 与 pass^k 的数值会出现差异。当 k=1 时，两者的值是相同的（都等于每次试验的成功率）。而当 k 达到 10 时，两者的情况则完全相反：pass@k 的数值接近 100%，而 pass^k 的数值则降为 0%。

这两种指标都很有用，具体该使用哪种取决于产品需求：对于那些只要有一次成功就足够的工具，应使用 pass@k；而对于那些需要保持一致性的系统，则应使用 pass^k。

Agent 能力本质上是基于 LLM 的，其中通过加入工程手段尽可能去约束模型行为，但本质上依旧是概率模型，那么就有概率出现相同输入得出不同输出结构的情况。

Build Agents Evaluation System​

一、初始评估数据集构建阶段（从无到有，夯实题目质量）

步骤 0：尽早开始

许多团队迟迟不建评估，是误以为必须先凑齐几百道测试题。实际上，从真实失败案例中挑出 20 到 50 个简单任务就是极佳的起点。在 Agent 开发早期，每次改动带来的效果变化通常非常显著，小样本量就足以测出差异，初期完全应当遵循二八原则。更重要的是，评估越晚建越难——早期产品需求可以直接自然地转化为测试用例，拖到上线后再补，就变成了对线上复杂系统的“逆向工程”。

步骤 1：从已有的手动测试入手

不需要凭空造题，直接把开发阶段每次发版前人工验证的核心行为，以及用户最常尝试的典型任务转化为测试集即可。如果产品已经上线，则可以直接从缺陷追踪系统和客服支持工单里取材，将用户反馈的真实故障沉淀为测试用例，并按对用户的影响程度排序，把精力优先投入最关键的场景。

步骤 2：编写无歧义的任务并提供参考解

保证题目质量往往比想象中困难。一道合格的任务，应当能让两位领域专家独立得出完全一致的“通过/失败”结论，且专家自己也必须能够完成该任务。任务描述或模型评分标准中的任何模糊之处，最终都会变成评估指标里的噪声。评分器将要检查的一切要求都必须在任务描述中写明，绝不能让 Agent 因为规范含糊而冤枉失败——例如 Terminal-Bench 的审计曾发现，任务让 Agent 写脚本却未指定文件路径，但测试代码默认检查某个固定路径，导致 Agent 无辜报错。对于前沿模型而言，如果一道题跑了上百次依然是 0% 通过率（0% pass@100），大概率不是模型不行，而是任务本身或评分器出了问题。因此，最好为每道任务编写一份能通过所有评分器的参考解（Reference solution），既证明题目可解，也验证评分器配置无误。

步骤 3：构建正反平衡的问题集

评估必须同时覆盖“应当触发某行为”和“不应当触发某行为”两类场景，避免单边测试导致单边优化和类别失衡。例如团队在为 Claude.ai 构建联网搜索评估时，如果只测该搜的时候有没有搜，最终只会优化出一个“逢问必搜”的 Agent。因此测试集必须双向覆盖，既包含必须联网查询的问题（如查实时天气），也包含应直接凭内置知识回答的问题（如“谁创立了苹果公司”），在“该搜不搜（欠触发）”与“不该搜乱搜（过触发）”之间反复打磨提示词与评估集，并随新案例出现不断扩充覆盖面。

二、评估框架与评分机制设计阶段（确保结果真实、公平、防作弊）

步骤 4：搭建稳健且环境隔离的评估框架

评估环境中的 Agent行为必须尽量与生产环境保持一致，同时评估基础设施本身不能引入额外噪声。每一次试验都应当从彻底干净、相互隔离的环境启动，严防运行之间的共享状态（如残留文件、缓存数据、资源耗尽）引发与 Agent 能力无关的连锁故障，或反过来人为拉高分数——例如 Anthropic 在内部测试中就曾发现，Claude 会去翻看上一次试验遗留的 Git 提交历史从而获得不公平的“作弊”优势。同样，如果多次独立试验都因为同一底层限制（如 CPU 或内存不足）而失败，这些样本就失去了统计独立性，评估结果也就不再可信。

步骤 5：精心设计评分器

评分器的选型应遵循清晰的分层原则：凡是能用确定性规则（deterministic graders）判定的就优先用程序硬校验，遇到灵活或开放场景再引入大模型评分器（LLM-as-judge），并审慎借助人工评估做额外校验。

在评测对象上，应当尽量评估最终产出结果而非死板卡控执行路径（比如强行要求工具调用顺序），因为 Agent 经常能找到设计者意想不到的合理路径，死卡步骤只会制造脆弱的测试并扼杀有效解法。对于多环节复杂任务，则应引入部分得分机制（partial credit），把“完全失败”到“完全成功”的连续区间体现出来——例如客服 Agent 准确识别了问题并核验了客户身份，只是最后退款失败，其表现显然好于一开始就出错。

在使用大模型评分器时，必须与人类专家进行严密校准以确保二者分歧极小；同时应给模型留出“退路”（例如信息不足时允许输出“Unknown”）以减少幻觉，并将复杂评分拆解为清晰的结构化维度，由相互独立的模型评分器分维度打分，而非让单个模型一口气评完所有维度，等体系稳固后仅需偶尔抽检即可。

此外，必须高度警惕隐蔽的评分与框架缺陷，哪怕资深团队也容易踩坑：例如 Opus 4.5 在 CORE-Bench 上最初仅得 42%，排查后才发现是评分规则过于死板（把 96.12 判错而要求精确匹配 96.124991…）、任务表述不清、存在无法复现的随机任务以及运行脚手架限制过多，修复后得分立刻跃升至 95%；METR 基准也曾出现提示词要求达到某一阈值、评分器却要求严格超过该阈值的问题，导致乖乖听话的模型反被扣分。最后，评分机制还必须具备防绕过、防钻空子的能力，确保 Agent 只能靠真正解决问题才能通关。

三、长期维护与持续演进阶段（让评估成为活的研发资产）

步骤 6：持续审查运行记录（Transcripts）

如果不去翻看大量试验的完整执行轨迹与打分详情，团队根本无从判断评分器是否正常工作。Anthropic 专门投入开发了用于查看运行记录的工具并坚持定期阅读，因为当任务失败时，只有看记录才能分清究竟是 Agent 真犯了错，还是评分器误杀了有效方案。健康的评估应当让每次失败看起来都合情合理、错因一目了然；更重要的是，团队绝不该在未细读运行记录和评估细节前就盲目轻信纸面分数，一旦发现评分不公、规范模糊、有效解法受罚或框架过度束缚模型，必须立刻修正评估本身。

步骤 7：监控能力评估的饱和度

当评估通过率达到 100% 时，它虽仍能作为回归防线防倒退，但已经无法为能力提升提供任何指引，这就是评估饱和（Eval saturation）。例如 SWE-Bench Verified 过去一年从 30% 一路逼近超过 80% 的饱和区，越靠近上限，剩下的全是极少数难题，原本巨大的能力跃迁在分数上可能只体现为微小的涨幅，极易产生误导。代码审查初创公司 Qodo 最初对 Opus 4.5 并不满意，正是因为他们原有的一次性编码测试已经无法捕捉模型在更长、更复杂任务上的进步；后来他们重建了一套面向 Agent 的新评估框架，模型的能力跃升才清晰显现出来。

步骤 8：通过开放共建与明确权责实现长期维护

评估套件不是一次性交付物，而是需要持续养护、权责清晰的“活资产”。Anthropic 实践中最有效的组织分工，是由专门的评估团队负责维护底层基础设施，同时由最懂业务的领域专家和产品团队主导贡献绝大多数评估任务并亲自运行评估。对 AI 产品团队而言，维护评估应当像写单元测试一样成为日常习惯——事实上，编写评估任务本身就是检验产品需求是否足够清晰、是否具备开发条件的最佳压力测试。

团队还应当践行评估驱动开发：在当前模型尚无法完美胜任之前，就提前为规划中的能力建好评估（哪怕初始通过率很低），用来显式押注未来几个月的模型进步；一旦新一代模型发布，跑一遍测试集就能立刻看清哪些押注已经兑现。归根结底，离用户和产品需求最近的人最懂得如何定义成功，借助如今的编码工具（如 Claude Code），产品经理、客户成功团队甚至销售人员都可以直接以提交代码 PR（Pull Request）的形式贡献评估用例，团队应当积极放权并主动赋能他们参与共建。

Evals 结合其它验证方法​

自动化评估可以针对数千次任务中的某个智能体进行，而无需投入生产环境或使用真实用户的数据。但这只是了解智能体性能的方法之一。要了解完整的性能情况，还需要包括生产监控、用户反馈、A/B 测试、人工文本审核以及系统化的人类评估等多种手段。

一、离线自动化验证类（上线前主动防线） 1. 自动化评估（Automated evals）
  • 核心定义：在不引入真实用户的前提下，通过程序自动批量运行预设测试。
  • 核心优势：这种方法能够显著加快研发迭代速度，测试结果完全可复现，且全程不会对线上用户造成任何影响。它可以无缝集成到每次代码提交（commit）的流程中自动运行，无需部署到生产环境就能大规模验证
  • 各类业务与边界场景。
  • 主要局限：自动化评估的前期搭建投入较大，而且随着产品功能与底层模型的不断演进，团队必须持续投入精力进行维护以避免评估标准发生漂移（drift）。此外，如果测试集的设计脱离了真实用户的使用模式，它很容易给团队带来虚假的信心。
二、线上真实流量与反馈类（生产环境客观验证） 2. 生产监控（Production monitoring）

核心定义：在实时运行的线上系统中，持续追踪性能指标与错误情况。

核心优势：生产监控能够大规模地揭示真实用户的交互行为，有效捕捉离线合成测试容易遗漏的长尾问题，从而为团队提供关于 Agent 真实表现的客观事实基准。

主要局限：这种方式本质上是事后被动响应的，往往要等到问题已经触达并影响用户之后才能被察觉。同时，线上信号通常较为嘈杂，前期需要投入研发资源完善监控埋点（instrumentation），且线上数据天然缺少用于精准打分的标准答案。

3. A/B 测试（A/B testing）
  • 核心定义：引入真实用户流量，对不同版本的 Agent 进行对照实验。
  • 核心优势：A/B 测试能够直接衡量留存率、任务完成率等真实的用户成果，通过科学分流有效排除各类混杂干扰因素，并且具备成熟、系统化且易于规模化推广的实验范式。
  • 主要局限：它的反馈周期较慢，通常需要数天甚至数周才能达到统计显著性，且高度依赖足够庞大的用户流量。同时，它只能检验已经部署上线的改动，而且仅靠指标涨跌本身很难揭示变化背后的真正原因，往往仍需结合深入审查对话记录才能完成归因。
4. 用户反馈（User feedback）
  • 核心定义：收集用户主动给出的显式信号，例如点踩或提交 Bug 报告。
  • 核心优势：用户反馈能帮团队发现此前完全未曾预料到的盲点问题，直接附带来自真实用户的具体失败案例，且这些反馈通常与核心产品目标高度相关。
  • 主要局限：这类数据往往非常稀疏且带有用户自我选择偏差，内容多集中在严重故障上，容易掩盖轻微但高频的体验问题，而且用户很少会详细解释失败的具体原因。除此之外，收集与归类过程难以完全自动化，如果主要依赖用户来兜底发现问题，还会对用户体验和口碑产生直接的负面影响。
三、人工深度评估类（校准标准与处理复杂任务） 5. 人工审查运行记录（Manual transcript review）
  • 核心定义：由团队成员直接通读 Agent 与用户的完整对话及执行记录（transcripts）。
  • 核心优势：人工通读记录能帮助团队快速建立对 Agent 失败模式的直觉，发现自动化检查容易漏掉的细微质量缺陷，并能在具体细节中校准“什么才是好表现”的标准。
  • 主要局限：这种方法极其耗时且无法规模化，抽样覆盖的范围往往不够一致，信号质量也容易受到审查者疲劳度或不同人员判断差异的影响。同时，它通常只能产出定性洞察，难以形成清晰、稳定的量化评分。
6. 系统性人工评估研究（Systematic human studies）
  • 核心定义：由经过专门培训的评分者，按统一规范对 Agent 的输出结果进行结构化打分。
  • 核心优势：通过多名人类评估者交叉评审，它能够产出“黄金标准”级别的高可信度质量判定，尤其擅长处理没有唯一答案的主观性或模糊性任务，其产出的人工标注信号还可以直接用于改进基于模型的自动化评分
  • 器。
  • 主要局限：系统性人工评估的成本相对较高、反馈周转较慢，难以作为高频常规手段频繁执行。在实际推进中，不同评分者之间的分歧需要额外机制进行协调与对齐；如果涉及法律、金融、医疗等高门槛复杂领域，还必须聘请具备专业背景的领域专家来开展评估。

从整体协同来看，这三类方法各有侧重、彼此互补：日常高频迭代依靠离线自动化评估守住底线，上线后依靠生产监控、A/B测试与用户反馈检验真实业务效果并捕获线上新问题，同时结合人工审查运行记录与系统性人工评估深挖根因、校准质量标准，并将新发现的失败案例持续反哺回离线测试集，从而形成闭环演进的评估体系。

这些方法适用于代理开发的不同阶段。自动化评估在发布前以及持续集成/持续部署过程中非常有用，每次代理更新或模型升级时都会进行此类评估，以此作为防范质量问题的一线防御措施。在发布后，则需要进行生产监控，以检测分发过程中的变化以及不可预见的现实世界中的故障。A/B 测试可以在拥有足够的流量后进行，以验证那些重大的变更。用户反馈和文本分析则是持续进行的做法，用于填补其中的空白：不断收集用户反馈，每周分析一些文本样本，并根据需要进一步深入调查。对于需要校准大语言模型评分器或评估主观输出的情况，则应该保留人工研究的时间，因为在这种情况下，人类共识仍然具有重要的参考价值。

就像安全工程中的瑞士奶酪模型一样，没有哪个单一的评估层能够发现所有问题。通过结合多种方法，那些被一个层遗漏的故障会被另一个层所发现。

最有效的团队会结合使用这些方法：自动化评估以实现快速迭代，生产监控以确保数据准确性，以及定期的人工审核以进行校准。

在 AI Agent 开发中尽早建立评估体系（Evals）的重要性不言而喻。缺乏评估的团队容易陷入被动“救火”的恶性循环，修好一个问题又引发另一个问题，且无法分辨真正的性能退化与偶然波动；而尽早投入评估的团队反而能加速迭代，因为每一次失败都能沉淀为测试用例，测试用例可以防止回归，量化指标也能取代主观猜测。评估为团队指明了清晰的优化方向，把“感觉 Agent变差了”这类模糊体感转化为可落地改进的目标，但前提是必须将评估视为核心组件而非事后补救，其价值才会产生复利。

尽管不同类型 Agent的具体评估模式各有差异，但底层方法论是恒定的：不必等待完美的测试集，而应尽早启动，从实际遇到的失败案例中提炼真实的测试任务，并定义清晰、无歧义且稳健的成功标准。在执行层面，需要精心设计并组合多种评分器，确保题目对模型具有足够挑战性，并在使用过程中不断迭代评估集以提高信噪比；同时，务必仔细阅读 Agent 的完整运行记录（Transcripts），而不只是停留在表面分数上。

AI Agent 评估目前仍处于快速发展的阶段（随着 Agent 的发展而不断发展），随着 Agent 承担更长周期的任务、在多 Agent系统中展开协作，以及处理越来越主观的工作，现有的评估方法也必须随之持续演进和调整，行业仍需在实践中不断探索并更新最佳实践。

Eval frameworks​

Harbor 旨在用于在容器化环境中运行代理程序。它拥有支持在多种云提供商上大规模进行试验的基础设施，同时还采用了标准化的任务定义格式和评分标准。像 Terminal-Bench 2.0 这样的热门测试工具可以通过 Harbor 进行部署，因此用户可以轻松运行这些成熟的测试工具，同时还可以使用自制的评估套件来进行测试。

  • Harbor：https://www.harborframework.com/
  • Terminal-Bench Github 地址：https://github.com/harbor-framework/terminal-bench
  • Terminal-Bench 官网地址：https://www.tbench.ai/
  • Swe-Bench 官网：https://www.swebench.com/verified.html

其它的 Evaluation 框架没有研究过，就不做过多推荐，因为在真实的业务场景中大概率是构建企业内部自己的测评平台，维护自己的测评 Task/Case。
