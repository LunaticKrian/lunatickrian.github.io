【年终总结】25 Summery，26 All in AI

2026年1月24日 · 阅读需 8 分钟

Summary​

2025年就此结束了，这篇文章主要是为了记录2025年开始从后端转型AI的一个阶段性记录，算是一个年终总结吧，同时也是2026年继续在AI的技术路线上的一个规划。

很长一段时间没有更新知乎了，一方面是本职工作实在太忙了（当然是一个借口，毕竟时间是海绵里的水挤挤总会有的），从传统后端转型到LLM开发方向需要补充的基础知识太多； 另一方面在构建我的【个人博客网站】（所有的更新都会第一时间更新到这个站点上，然后会同步到各个平台，目前是这样计划的）

在知乎记录系统性的学习笔记还是对于我个人而已太局限了，在使用习惯上还没有养成。我没办法像我的个人博客那样做很好的系统性归类管理（即使提供专栏功能）。

基于此，我在想是否把知乎当作我记录日常学习，分享想法和及时对外交流的一个平台，而不是做只围绕某一个主题的系统更新，机械化发布文章的地方，更多的还是基于每次的学习收获及时分享或许会更好。

AI 新方向 start​

回到我的年终总结，发生职业规划变更的时间节点应该是在2024年年底，公司内部开始构建私有化的大模型对话平台，我有幸参与到了其中，团队用了两周的时间最终在25年元旦前夕完成了第一版平台的上线。

时间来到24年春节前后，DeepSeek R1发布爆火，一时间全国上下都炸了......公司开始向AI资源倾斜，开始不断在业务场景上探索AI的应用能力。

最开始团队的技术选型是Java，但是由于Spring AI的正式版迟迟没有发布，我们被迫在生产环境中使用了Spring AI的 Snapshot 版本。 然后，由于团队配置不齐没有AI Infra同学，模型流式接口没有办法正常接入SSE，最终没有办法使用 WebFlux 进行异步拆包响应前端......然后是探索 RAG 构建企业内部知识库，这又是一个大活，不同的数据源，不同的数据结构，多模态数据...... MCP 模型上下文工具调用协议发布、A2A协议、多Agent交互......大模型应用在24年的发展太快了，反馈到研发身上的就是加班，加班，加班... 24年一整年几乎都在加班，最长的一次是两月无休......虽然过程艰难，但也后收获，算是搭上了AI的车，技术栈从原来的Java有了些扩展，Python、Golang都在工作中使用起来了，对Agent有了更深的认识等等。

Context Engineering​

影响模型输出效果的除了模型本身的能力（参数量）外，更重要的其实还是上下文的构建，从年初的Prompt Engineering 到前端时间提出的 Anthropic 提出的 Context Engineering， 通过调整模型输入的 Prompt 比通过微调模型性价比更高。基于此背景，最近也在研究探索 Context Engineering 相关的工程化方案，例如 长短期记忆的构建、遗忘策略、Memory服务等等。从工程角度出发，Context Engineering 一定是未来提升模型输出效果最直接且成本最低的方式。

当然Context Engineering 的涉及范围比较广并不仅仅局限于对话 Prompt 的上下文，而是包含了 Memory、RAG、Tools Call等等。有兴趣的同学可以看看官方的这篇文章： https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

AI Agent to Agentic AI​

整个25年我们都在构建各种 LLM Workflow、AI Agent，慢慢的我们发现所有的Agent都是独立的为某一个业务场景定制化的开发，当业务场景与业务场景之间发生交互时，我们依然依赖于传统的系统调用，通过开放 API 接口的方式去完成业务边界之间的交互，也没有将零散的 Agent 边界打通，依然采用的系统之间的相互调用，而不是 利用模型的能力实现 Agent To Agent 之间的协作。 AI Agent 能够访问预测性、生成式和其他 AI 功能，Agent 的角色被设定为实现特定目标，其运行不依赖用户提示（例如针对生成式内容的提示）。而 Agentic AI 能分析实现一项目标的各种路径，判断并选择可完成工作任务的理想方法。此外，AI Agent 还会考虑过往工作的执行记录来优化工作结果。 Agentic AI 系统则更进一步，本质上是一种AI 系统，它能够自主地基于历史情况和对当前需求的评估结果来制定决策，尽可能减少人为监督的需要，能够将各种 AI agent 以及其他系统/工具融合成为一个更紧密的整体。例如，AI agent 可以处理客户投诉。随后，Agentic AI 系统会利用这些数据来帮助产品设计师和营销主管基于客户行为模式优化自身工作。

Agentic AI 相比于 AI Agent 更加依赖于 Context Engineering 的能力建设，因此在26年的Q1 将会all in 模型上下文构建能力的建设，整合现有的Memory 记忆，RAG 检索、MCP 工具调用等能力去构建一个完善的 Agentic Context Ability 服务于上层的 Agentic System。

Cursor + Claude Coding LLM 杀手级应用

要说25年中对我职业生涯中最有冲击力的一件事是 Cursor 1.0 + Claude 4.5 编程模型的发布，AI Coding IDE 的出现极大程度的提高了无论是研发还是非研发人员的效率。在25年年初，我对AI Coding 工具的使用权重可能在10%左右，本质上是还是模型能力的不足，具体可以参考下面问题中基于我的个人看法的回答：

如何看待现阶段坚持不用 AI 的 「古法编程」？

到目前为止，AI Coding 在我日常开发过程中的使用占比已经来到了55开的地步，甚至在某些需求场景中能占比到70%甚至更高。通过自然语言来进行 Coding，完全改变了传统的开发模式，极大程度的提高了开发效率。当然，使用这些 AI Coding IDE 需要一个正确的姿势，并不是所有的场景都可以无条件相信AI，用 AI Coding 和 用好 AI Coding 是两件事。

最大的一个转变我认为是从 Coder 转变为 Reviewer，以前可能需要花费70%的时间在写代码上，现在可能需要花70%的时间在 Review AI 生成的代码上。目前 AI Coding 还很难做到需求的端到端交付，但是我觉得从它能力本身上来说替代我绰绰有余（我哭死，毕竟我不是什么语言都会，什么需求都能写，但它是真可以呀！！！）

但是从另一个角度来看，高昂的 Token 消耗费用（成本问题）、以及三方的应用 + 闭源模型（数据泄露风险），出现了小公司用不起，大公司不能用的情况。但这不妨碍它是一个非常优秀乃至顶级的 Agentic 应用。

学编程到底是学 API 还是学 Design？

当我离开校园走入职场后，一直有个困惑：学编程到底是在学 API 还是在学 Design？

在25年中前，我一直坚持的是：学编程是学API！在之前无论是学生生涯还是职场生涯都几乎都是在学习各种框架、各种库，习惯了接受、使用而不是定义，不是创造。我觉得这也是大多数人一直在走的路，Spring 更新了 Spring AI，OK 第一时间查看官方文档，先看看是怎么使用，本地启一个 Demo 服务，看看怎么和 LLM 进行联动交互，MCP 工具注解定义怎么使用......最终还是停留在使用层面，我感觉我似乎已经习惯了拿来用就可以的思维模式，当在研发过程中遇到问题的第一反应是寻找能直接三方库，能用能完成需求即可，很少会去思考它背后的设计。

大模型的爆发式发展颠覆了我对走编程这条路的认知：学习API是在AI时代下投入产出比最低的学习方向。学习设计系统化思想、架构设计、抽象协议我认为比学习API更有价值。知道什么是 IOC、AOP，怎么用 IOC、AOP 没有太大意义，知道为啥会有 IOC、AOP，IOC、AOP 解决了什么问题更有意义。前者是在学 API，学怎么用；后者是在学设计，学抽象。可能例子举得不是很恰当，我只是想表达一个观点：AI 时代下死磕API没有任何意义，学习设计思想、结构化能力、抽象能力更重要。学会去定义，去创造比只会接收会让你走得更远。
